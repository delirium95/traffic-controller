# VPSProxy-like proxy (власна реалізація)

Мінімальний, але робочий аналог VPSProxy: **PHP-шлюз(и) + локальний Rust-клієнт**
з multi-hop onion-шифруванням (AES-256-GCM, окремий ключ на кожен хоп).

```
Браузер → 127.0.0.1:2222 (клієнт) → gate_1.php → gate_2.php → ... → gate_N.php → цільовий сайт
          HTTP forward-proxy         onion: кожен вузол знімає один шар шифрування
```

- **gate_1** знає клієнта, але не знає цілі.
- **gate_N** (вихідний) знає ціль, але не знає клієнта.
- Вміст запиту до цілі зашифрований ключем вихідного вузла — проміжні його не читають.
- Відповідь шифрує вихідний вузол своїм ключем; проміжні лише ретранслюють байти.

## Склад

| Файл | Що це |
|------|-------|
| `gate/gate.php` | Один PHP-файл. Завантажується на кожен веб-хост. Вміє бути проміжним (`forward`) або вихідним (`target`) вузлом. |
| `src/bin/proxy_client.rs` | Локальний клієнт — HTTP forward-proxy на `127.0.0.1:2222`. |
| `vpsproxy.example.toml` | Приклад конфігу (список вузлів ланцюга). |

## 1. Згенерувати ключі

Для кожного вузла — окремий ключ (32 байти = 64 hex):

```bash
openssl rand -hex 32
```

## 2. Налаштувати й залити gate.php

Для кожного хоста зроби копію `gate/gate.php` і впиши **його** пароль та ключ:

```php
const GATE_PASSWORD = 'пароль-для-цього-вузла';
const GATE_KEY_HEX  = 'сюди-64-hex-з-openssl';
```

Залий на веб-сервер з PHP (потрібні розширення `openssl` і `curl`), напр.
`https://host-a.example.com/gate.php`. Бажано **HTTPS** — тоді й транспорт між
клієнтом і вузлами шифрований TLS поверх onion.

## 3. Налаштувати клієнт

```bash
cp vpsproxy.example.toml vpsproxy.toml
```

Впиши вузли у тому ж порядку, що й ланцюг. **Останній** `[[gate]]` — вихідний.
`key`/`password` мають точно збігатися з тим, що в кожному `gate.php`.

## 4. Запустити

```bash
cargo run --bin proxy_client -- vpsproxy.toml
```

Налаштуй у браузері **HTTP-проксі** → `127.0.0.1:2222` (у Firefox: Settings →
Network Settings → Manual proxy; за бажання вимкни «proxy DNS»/залиш як є).

## HTTPS (MITM-CA)

Браузер для `https://` відкриває тунель через `CONNECT`. Клієнт термінує цей TLS
локально сертифікатом, який на льоту підписує **власний локальний CA**, а реальну
ціль тягне вихідний вузол (`gate.php` через cURL уміє https).

Щоб браузер довіряв:
1. Запусти клієнт один раз — він створить `vpsproxy-ca/ca_cert.pem` (+ `ca_key.pem`).
2. Імпортуй `ca_cert.pem` у довірені кореневі ЦС браузера/ОС.
   - Firefox: Settings → Privacy & Security → Certificates → View Certificates →
     Authorities → Import → познач «Trust this CA to identify websites».
   - macOS: Keychain Access → System → Import → став Always Trust.
3. Пропиши у браузері **і HTTP, і HTTPS/SSL** проксі на `127.0.0.1:2222`.

> `ca_key.pem` — приватний ключ, яким підписуються сертифікати на будь-який домен.
> Тримай його лише локально; не коміть, не передавай. Якщо витік — видали CA-теку
> й прибери імпортований CA з довіри.

## Рандомні ланцюги

У `vpsproxy.toml`:

```toml
mode = "random"   # замість "sequential"
hops = 3          # скільки вузлів у ланцюзі на кожен запит
fixed_exit = true # тримати останній [[gate]] постійним виходом
```

- `random` + `fixed_exit=false` — на кожен запит випадковий підбір і порядок вузлів,
  вихід теж випадковий.
- `random` + `fixed_exit=true` — вихід фіксований (останній `[[gate]]`), решта хопів
  добираються випадково. Корисно, коли цільовий сервіс очікує стабільний IP виходу.

## Перевірено (end-to-end, реальний AES-256-GCM)

На mock-вузлах, автоматичні тести:

- ✅ sequential, plain HTTP GET крізь 3-вузловий ланцюг;
- ✅ random mode (fixed_exit) — 5/5 запитів;
- ✅ **HTTPS через MITM (CONNECT)** крізь 3 вузли до реального `https://example.com` → 200;
- ✅ POST з UTF-8/emoji тілом — байти цілі;
- ✅ неправильний ключ/пароль → `502` з **назвою ланки**, що впала
  (`chain error: GATE-ERROR: downstream GATE-ERROR: bad password`).

## Поточні обмеження (і куди рости)

- Тіло запиту читається за `Content-Length` (chunked upload без довжини не
  підтримано). Відповідь буферизується повністю (без стрімінгу великих файлів).
- Keep-alive є; HTTP/2 між браузером і клієнтом нема (TLS ALPN за замовчуванням
  домовиться на HTTP/1.1).
- Нема локального кешу IP і «замаскованих» (cookie) шлюзів з оригіналу — додається
  зверху за потреби.
- MITM означає, що клієнт бачить твій трафік у відкритому вигляді (він же його й
  тягне). Довіряй лише **своєму** клієнту на **своїй** машині.

## Безпека / межі використання

Інструмент подвійного призначення. Він для **законних** сценаріїв: власна
приватність, обхід блокувань власного трафіку, навчання мережам/крипто. Не
використовуй для обходу антифроду, фарму акаунтів, кардингу тощо — і я з таким
не допомагатиму.

- Паролі/ключі в `vpsproxy.toml` і в `gate.php` — секрети. `vpsproxy.toml`
  додано в `.gitignore`; не коміть реальні ключі.
- GCM автентифікує дані: підміна/пошкодження на будь-якому хопі → `decrypt failed`.
- Міняй ключі ротацією (новий `openssl rand -hex 32` з обох боків).
